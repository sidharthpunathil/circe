MCP servers

A skill teaches the agent a procedure. A server gives it something to reach: a database, an API, a browser, your issue tracker.

  1. 1 Add one on the MCP tab. Give it a command (npx …) or a URL, pick the transport, and name the environment variables it needs. Or paste a .mcp.json you already have on the Import page.
  2. 2 Put it in a folder, alongside whatever else that kind of project needs.
  3. 3 In the project, run the command below.
{{ template "cmd" (printf "circe mcp %s" .Folder) }}

That merges them into the project's .mcp.json. Servers the project already has are reported and left alone unless you pass --force, and any top level keys Circe does not model are carried through untouched.

Your keys are never stored here

Circe records the name of each variable a server needs, never its value. The generated config refers to it as ${VAR}, so the value comes from your own shell. After installing, the CLI tells you which are still unset: 

2 added in .mcp.json
set these before the servers will start:
  DATABASE_URI                  postgres
  GITHUB_PERSONAL_ACCESS_TOKEN  github · optional

It also means a share code can never leak a token.

Rules

Skills teach Claude how to do something. Rules tell it how you work: the text that ends up in a project's CLAUDE.md or AGENTS.md. Each rule picks which files it belongs in.

{{ template "cmd" (printf "circe rules %s" .Folder) }}

They merge into the project's own files inside a marked block, so anything you wrote outside it is untouched and re-running replaces only that block: 

<!-- circe:start {{ .Folder }} -->
<!-- Managed by circe. Edits inside this block are replaced on reinstall. -->

  …the folder's instructions, then its rules…

<!-- circe:end {{ .Folder }} -->

--context=skip leaves the file alone, --context=overwrite replaces it wholesale.

Skills

A skill is a SKILL.md plus whatever ships beside it. Install a single one without involving a folder:

{{ template "cmd" (printf "circe add %s" .Skill) }} {{ template "cmd" "circe list" }} {{ template "cmd" "circe pull" }}

Installed skills are recorded in circe.json, so pull restores the same set on any machine. Local edits are never clobbered: pull holds back anything you have changed unless you pass --force, and list shows what has drifted.

Going the other way, publish a library you already have on your own machine. This is the answer for a hosted registry, whose Import page can only read the filesystem of the machine it runs on:

{{ template "cmd" "circe push ~/.claude/skills" }}

Without the CLI

This registry publishes a Claude Code marketplace manifest, so folders install with stock Claude Code and no extra tooling.

{{ template "cmd" .MarketplaceLine }}

Run that inside Claude Code. Each folder here shows up as a plugin.

Someone else's registry can hand you a folder without any setup at all. Paste their code into Import → From a code, or run:

{{ template "cmd" "circe import sb_…" }}

Backup and sync

{{ if .Synced }}

This registry is connected to {{ .SyncRepo }}. Push from Settings and everything here is written there as ordinary markdown and JSON, and committed.

{{ else }}

Connect a GitHub repository on Settings and push: every skill, rule, server and folder is written there as ordinary markdown and JSON, and committed. Your library becomes something you can read in a browser, review in a pull request, and restore anywhere.

{{ end }}

Or take a copy on the machine running the server, in the same layout:

{{ template "cmd" "circe-server export -out ./my-library" }} {{ template "cmd" "circe-server import -in ./my-library -force" }}

Access tokens and share codes are never written by either. A token in a repository is a token that has leaked, and a share code works without this registry's passcode.
